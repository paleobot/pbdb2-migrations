## Context

The `persons` table has been restructured to move flat attribute columns (`given_name`, `family_name`, `middle`, `email`, `orcid`, `country_code`, `institution`, `gender_id`) into a single `person jsonb NOT NULL` column. The DDL and payload schema (`person.schema.js`) are already in place. Two migration scripts must be updated to target the new structure: `migrate-persons.js` (MariaDB source) and `migrate-pbot-persons.js` (PBot GraphQL source). Additionally, `migrate-pbot-refs.js` has a downstream query that references flat person columns.

The new DDL:
```sql
CREATE TABLE persons (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    password text,
    role_id integer REFERENCES dictionaries.roles("id") NOT NULL,
    person jsonb NOT NULL,
    authorizer_person_id integer REFERENCES persons("id") NOT NULL,
    active boolean,
    total_hours numeric
);
```

## Goals / Non-Goals

**Goals:**
- Update `migrate-persons.js` to build a `person` JSONB object instead of inserting flat columns
- Update `migrate-pbot-persons.js` to build JSONB, query JSONB paths for match cascade, and use `jsonb_set` for backfills
- Replace `gender_id` FK lookup with inline gender string mapping in both scripts
- Store legacy IDs (`oldpbdbID`, `pbotID`) in the JSONB `legacyIDs` object
- Update downstream queries in `migrate-pbot-refs.js` to use JSONB paths for enterer lookup

**Non-Goals:**
- Updating `migrate-refs.js` or `migrate-pbot-refs.js` beyond the enterer lookup query (table rename and legacyIDs nesting issues are tracked separately)
- Changing the payload schema or DDL (already done)
- Modifying the `dictionaries.genders` table (retained for future API use)

## Decisions

### 1. Build JSONB in JavaScript, insert as a single parameter

Both scripts will construct a plain JavaScript object for the `person` JSONB column, then pass it as a single `$N` parameter. PostgreSQL's `pg` driver automatically serializes JS objects to JSONB.

**Alternative considered:** Building JSONB in SQL with `jsonb_build_object()`. Rejected because the JS approach is simpler to read, lets us conditionally omit properties (empty email, null orcid, etc.) before serialization, and matches the pattern used in `migrate-pbot-refs.js` for reference JSONB.

### 2. Gender: direct string mapping, no dictionary lookup

Both scripts will map gender to a string value directly (`'M'→'Male'`, `'F'→'Female'`, default `'Anonymous'`) and place it in the JSONB. The `dictionaries.genders` query is removed from both scripts.

**Rationale:** The JSONB schema uses `enum: ["Male", "Female", "Other", "Anonymous"]`. A dictionary lookup adds a query and indirection for a four-value enum that won't change at migration time.

### 3. JSONB path queries for match cascade in `migrate-pbot-persons.js`

All match cascade queries change from flat column references to JSONB arrow operators:
- `WHERE orcid = $1` → `WHERE person->>'orcid' = $1`
- `WHERE lower(email) = lower($1)` → `WHERE lower(person->>'email') = lower($1)`
- `WHERE lower(given_name) = lower($1) AND lower(family_name) = lower($2)` → `WHERE lower(person->>'givenName') = lower($1) AND lower(person->>'familyName') = lower($2)`

The SELECT list also changes: `SELECT id, email, orcid` → `SELECT id, person->>'email' AS email, person->>'orcid' AS orcid` so the backfill null-checks continue to work without code changes to the JS logic.

### 4. Backfill with `jsonb_set` for matched persons

ORCID and email backfills use PostgreSQL's `jsonb_set` function:
```sql
UPDATE persons SET person = jsonb_set(person, '{orcid}', $1::jsonb) WHERE id = $2
```
The value must be passed as a JSON-encoded string (e.g., `'"0000-0002-5242-8573"'`), or constructed with `to_jsonb($1::text)`.

For `legacyIDs.pbotID` backfill on matched persons, a two-step `jsonb_set` may be needed if `legacyIDs` doesn't exist yet. Simpler approach: use the `||` merge operator:
```sql
UPDATE persons SET person = person || jsonb_build_object('legacyIDs',
  COALESCE(person->'legacyIDs', '{}'::jsonb) || jsonb_build_object('pbotID', $1::text)
) WHERE id = $2
```
This preserves any existing `legacyIDs` properties (e.g., `oldpbdbID` from the PBDB migration).

### 5. Omit empty/null JSONB properties rather than setting them to null

Properties like `email`, `orcid`, `countryCode`, `institution`, and `middle` are omitted from the JSONB when their source value is null or empty. This keeps the JSONB compact and matches the payload schema (these fields are not in the `required` array).

**How:** Build the JS object conditionally:
```js
const personJsonb = { givenName, familyName, gender };
if (email) personJsonb.email = email;
if (middle) personJsonb.middle = middle;
// ...
```

### 6. Downstream enterer lookup in `migrate-pbot-refs.js`

The enterer lookup query changes from:
```sql
WHERE lower(given_name) = lower($1) AND lower(family_name) = lower($2)
```
to:
```sql
WHERE lower(person->>'givenName') = lower($1) AND lower(person->>'familyName') = lower($2)
```

This is a one-line query change. The rest of the enterer resolution logic is unchanged.

## Risks / Trade-offs

**Performance of JSONB path queries** → The match cascade in `migrate-pbot-persons.js` runs ~87 queries against JSONB paths without indexes. With ~1,300 persons this is negligible. If the table grows significantly, GIN indexes on the JSONB column could be added later.

**JSONB merge for legacyIDs backfill** → The `||` merge operator overwrites the entire `legacyIDs` key. The `COALESCE` + nested merge pattern avoids this, but is more complex. Given that PBDB migration runs first (setting `oldpbdbID`) and PBot migration runs second (adding `pbotID`), the merge pattern is necessary to preserve both.

**No validation at migration time** → The JSONB objects built by the scripts are not validated against `person.schema.js` during migration. Invalid objects would be caught at API time but not during import. This is acceptable because the mapping is straightforward and tested, but could be mitigated by adding optional ajv validation in a future pass.

None — all design decisions are resolved based on the existing patterns in the codebase and the completed DDL/schema work.
