## Why

The surrogate `id` primary keys on the versioned tables are `integer GENERATED BY DEFAULT AS IDENTITY`. Because every edit inserts a *new version row*, `id` consumption scales with the number of edits, not the number of logical entities — so a versioned table burns through the ~2.1B `integer` range far faster than its entity count suggests. Occurrences-scale and refs-scale tables will get there.

Widening to `bigint` is a trivial greenfield edit now, but expensive later: once the tables carry data and cross-table FKs, PostgreSQL refuses `ALTER COLUMN ... TYPE` on a column under a foreign key, forcing a drop-and-recreate of every FK constraint in the graph. `bigint` is effectively free here — the hot FK graph is already integer-keyed, and 8 vs 4 bytes on keys is negligible — and it removes a latent exhaustion cliff.

External identity is unchanged: `permid` stays `uuid`. This change concerns only the internal surrogate keys.

## What Changes

- Widen `id` from `integer` to `bigint` (keeping `GENERATED BY DEFAULT AS IDENTITY`) on the in-scope solidified versioned tables: `refs`, `collections`, `schemas`, `characters`, `states`, `authorities`.
- Widen every FK column that references a widened `id` to `bigint`: the version-chain columns (`preceded_by_id`, `succeeded_by_id`) on each table, plus cross-references (`reference_id`, `parent_schema_id`, `parent_character_id`, `parent_state_id`, `collection_id`, `schema_id`) — including in the child tables `additional_collection_refs` and `additional_schema_refs`.
- Change the version-trigger helper function signatures to `bigint`: `swing_fks_to_new_version(target_table text, old_id bigint, new_id bigint)` and the `head_id` variable in `place_in_lineage()`.
- Leave `integer` in place for bounded tables: `persons.id`, all `dictionaries.*` ids, and therefore every `authorizer_person_id`, `enterer_person_id`, `role_id`, `reference_type_id` column.

Out of scope (design still in flux): `timescales`, `intervals`, `taxa`, `rank_opinions`, `assignment_opinions`, `rename_opinions`, `homonyms`, `occurrences`. These keep `integer` for now; FK columns in them that point at a widened table (e.g. `timescales.reference_id`, `occurrences.collection_id`) stay `integer` and are addressed when those tables are solidified. See design.md for why the resulting integer→bigint FKs are safe in the interim.

## Capabilities

### Modified Capabilities

- `entity-versioning-triggers`: the trigger helper functions and the versioned-table key design use `bigint` surrogate identifiers.

## Impact

- **postgresql/create_new.sql**: column type edits on 6 versioned tables + 2 child tables; two function signature edits. No behavioral/logic change.
- **Migration scripts**: no logic change, but node-postgres returns `int8` as a string (vs `int4` as a number) — the re-migration must confirm ids are handled as opaque values (see design.md and task 3.3).
- **Already-migrated tables** (`refs`, `collections`, `authorities`): rebuilt and re-migrated in the upcoming combined pass; no in-place `ALTER`.
