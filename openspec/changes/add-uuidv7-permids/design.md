## Context

All migration scripts currently produce `permid` values either as UUIDv4 (`crypto.randomUUID()` in `migrate-authorities.js`, `migrate-collections.js`, `migrate-refs.js`) or by reusing the external PBot `pbotID` (`migrate-pbot-refs.js`, `migrate-pbot-schemas.js`). The target schema declares `permid uuid NOT NULL` with no DEFAULT and no CHECK — the value is entirely app-supplied.

Each versioned table also has a `bigint GENERATED BY DEFAULT AS IDENTITY` primary key `id` and a `created_at timestamptz`. So insertion-order and chronological semantics are already owned by `id` and `created_at`; `permid` is purely the stable, permanent, cross-version public identifier.

We are already dropping and re-running the migrations for the bigint surrogate-key change, so this is a zero-marginal-cost moment to change permid generation. Generation is app-side, so this is independent of the (separately back-burnered) PostgreSQL 18 upgrade — it works on the current PG16.

## Goals / Non-Goals

**Goals:**
- Generate all in-scope permids (authorities, collections, refs, schemas, characters, states) as UUIDv7.
- Centralize generation in one shared ESM helper so future changes are one-line.
- Preserve the PBot `pbotID` in `legacyIDs` and re-key pbot idempotency/verification off it.
- Add a DB-level CHECK that rejects non-v7 permids, working on PG16 today.

**Non-Goals:**
- Upgrading the database to PostgreSQL 18 (native `uuidv7()` / `uuid_extract_version()`), which stays back-burnered.
- Changing `timescales` / `intervals` (design TBD).
- Any change to MariaDB reads, source-side value mapping, or non-permid columns.
- Backfilling or rewriting existing permids in place — the migrations are re-run from scratch.

## Decisions

**Decision: Use the `uuid` npm package's `v7()` rather than hand-rolling or `crypto`.**
Node's `crypto.randomUUID()` is v4-only with no v7 option. The `uuid` package is the de-facto standard, implements the RFC 9562 monotonic counter (strict intra-millisecond ordering), and is the natural shared choice with the API codebase that will also mint permids. Alternatives considered: hand-rolled ~15-line generator (rejected — we'd own bit-layout and monotonicity correctness for no real benefit); the standalone `uuidv7` package (viable but less likely to be the API's choice).

**Decision: One shared ESM helper module, imported by all permid-minting scripts.**
Keeps the generator swappable in one place (e.g. moving to native `uuidv7()` later) and guarantees migration and future API use the same source. Matches the project's ESM convention.

**Decision: Enforce v7 with `CHECK ((get_byte(uuid_send(permid), 6) >> 4) = 7)` on PG16 now.**
The version nibble is the high nibble of byte 6 of the UUID; `get_byte(uuid_send(...), 6) >> 4` reads it without a text cast and works on PG16. Alternatives: `substring(permid::text, 15, 1) = '7'` (readable but adds a text conversion per row); `uuid_extract_version(permid) = 7` (cleanest, but PG18-only). We adopt the `get_byte` form now and note the PG18 swap in the spec.

**Decision: Re-key pbot idempotency on `legacyIDs->>'pbotID'`, not permid.**
Generated permids change every run, so `ON CONFLICT (permid)` would duplicate rows. Cross-entity lookups already resolve via `reference->'legacyIDs'->>'pbotID'` (`lookupRefByPbotID`), so keying idempotency and verification on the same field is consistent and requires no new source of truth. For `migrate-pbot-refs.js` this replaces the `ON CONFLICT (permid)` upsert and the `WHERE permid = ANY(...)` verification. `migrate-pbot-schemas.js` has no permid-keyed upsert, so only its permid *generation* changes.

## Risks / Trade-offs

- **[Idempotency regression in pbot scripts]** → If `ON CONFLICT (permid)` / `WHERE permid = ANY(...)` are not migrated to the `legacyIDs.pbotID` key, re-runs silently duplicate every pbot reference. Mitigation: the pbot-refs spec delta makes the legacyIDs-keyed upsert and its scenarios a hard requirement; verification counts must be recomputed against `legacyIDs.pbotID`. A unique index or lookup-then-upsert on `reference->'legacyIDs'->>'pbotID'` is needed to make the upsert efficient and correct.
- **[Lost historical time-ordering of migrated permids]** → Accepted, not mitigated. Migrated permids encode migration time, not record creation time. `created_at` and the `bigint id` already provide real dates and insertion order, so `permid` was never the chronological key.
- **[CHECK form is PG16-specific bit-twiddling]** → Slightly obscure. Mitigated by a code comment and the spec note to swap for `uuid_extract_version(permid) = 7` on PG18.
- **[permid UNIQUE constraint + generated values]** → A generated v7 collision is astronomically unlikely, but the existing `references_permid_key` unique constraint remains the backstop; the idempotency logic (not the unique constraint) is what prevents duplicate *logical* rows on re-run.

## Migration Plan

1. Add `uuid` to `package.json`; create the shared ESM UUIDv7 helper.
2. Swap the three `randomUUID()` call sites to the helper (authorities, collections, refs).
3. Convert `migrate-pbot-refs.js`: generate permid via helper; move the upsert/verification onto `legacyIDs.pbotID`.
4. Convert `migrate-pbot-schemas.js`: generate permid via helper for schemas/characters/states (pbotID already in `legacyIDs`).
5. Add the CHECK constraint to the six in-scope permid columns in `postgresql/create_new.sql`.
6. Drop affected tables and re-run the migrations (combined with the bigint rebuild); verify no permid has version nibble ≠ 7 and pbot counts are stable across a second run.

Rollback: revert the scripts/schema and re-run; since the DB is rebuilt from scratch there is no in-place data to unwind.

## Open Questions

- Efficient idempotency mechanism for pbot-refs: a functional UNIQUE index on `(reference->>'legacyIDs'... )` to enable `ON CONFLICT`, versus an explicit lookup-then-insert/update. To be settled in implementation.
